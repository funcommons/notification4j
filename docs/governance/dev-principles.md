# 开发原则（通用版）

> 效力范围：本项目全部开发任务（后端/前端/数据库/测试/文档）
> 性质：**强制约束**。与产品原型/PRD 根规则、`docs/` 各设计文档冲突时先停下对齐，不得静默绕过。
> 初版：2026-08-22 · 通用版改写：2026-09-16

---

## 原则一：后端一律使用 framework4j 框架，禁止重复建设

### 1.1 能力映射（遇到下列需求，直接用 framework4j 对应模块）

| 需求场景 | framework4j 模块 | 禁止的自建行为 |
|---|---|---|
| 登录态 / JWT / Refresh 轮转 / 踢人 | `fwk4j-accesstoken`（@RequiresToken、TokenPair、revokeByUser） | 自写 JWT 签发校验、自管 refresh |
| 统一响应信封 / 错误码 | `fwk4j-api` + `fwk4j-web`（ApiResponse、ApiCode、GlobalExceptionHandler） | 自定义第二套信封/异常体系 |
| 接口签名防重放（开放/内部 API） | `fwk4j-signature`（@RequiresSignature、HMAC-SHA256、nonce） | 自写签名拦截器 |
| 限流 | `fwk4j-rate-limit`（@RateLimit、Lua 滑窗、Retry-After） | 自写限流器 |
| 缓存 | `fwk4j-cache`（@CacheableGet/Put/Evict、Caffeine+Redis、防穿透/击穿/雪崩） | 自写二级缓存、自拼 Redis key 逻辑 |
| 幂等键 | `fwk4j-idempotency`（Idempotency-Key、Redis SETNX、body hash、回放） | 自写防重复提交 |
| 审计日志 | `fwk4j-audit`（@Auditable、Hash Chain 防篡改） | 自写审计采集 |
| 字段脱敏 / 加密 | `fwk4j-sensitive`（@Sensitive、AES-256-GCM TypeHandler） | 自写加密工具类 |
| 分布式 ID | `fwk4j-id`（Snowflake、OpenID 混淆、WorkerIdStrategy） | 自写 ID 生成器 |
| 多数据源 / 多 Redis | `fwk4j-datasource`（@DataSourceOn）/ `fwk4j-redis`（@RedisOn） | 自写动态数据源路由 |
| 时间处理 / SQL 追踪 | `fwk4j-datetime` / `fwk4j-sql-tracing` | 自写序列化器/追踪 Filter |

版本锁定：`framework4j-all`（当前 v1.2.7，镜像至内部 Maven 仓）。业务 POM 禁写版本号。

### 1.2 framework4j 满足不了需求时——两条且仅两条出路

1. **自己实现，但必须人为确认**：在任务分支/评审单中写明「需求 → framework4j 现状差距 → 自建方案」，经后端 Lead（或架构组）**明确批准**后方可写代码；自建件必须放项目 `common` 模块统一维护，禁止散落各服务。
2. **提交 issue，要求 framework4j 升级实现**：登记 issue（标题=需求、复现差距、期望 API），纳入等待清单；framework4j 发版后**替换回框架实现**，删除自建过渡件。

无论走哪条路，都要在 `docs/adr/` 留一条决策记录（简版即可：差距/选择/回归计划）。**禁止的行为**：绕过确认直接自建、复制 framework4j 源码改巴改巴当自己的、同一能力各服务各写一份。

## 原则二：基于已有工程改造，尽量复用，不重复建设

- 存在遗留系统或参考工程时，本项目是**改造/扩建**，不是从零重写：认证、租户、权限、审计、通知、OSS、API Key、网关、协议适配、流式转换、路由选择/熔断等优先复用参考工程现成技术件（复用矩阵、改造清单、边界见 `docs/` 对应设计文档）。
- **明确不沿用**的是遗留业务模型而非技术件：与目标形态冲突的旧模型（如旧计费/倍率链、租户自注册）——按整改清单替换，不是重写底座。
- 判定阈值：单点改造成本 > 重写 50% 时才可选重写，且必须记 ADR；默认答案是复用改造。

### 2.1 复用源对照表（动手前先查）

**动手任何编码前，必须先扫两个源，确认"可复用则复用、属整改项则按整改"**：

| 源 | 角色 | 用法 |
|---|---|---|
| `参考/`（参考/遗留工程源码+文档） | **技术件复用真源** | 认证/租户/权限/审计/通知/OSS/API Key/网关/协议适配/流式转换/路由熔断/内容安全——先查 `参考/`，有现成件就改造复用，禁从零写 |
| 《优化建议清单》（对遗留系统的整改评估文档） | **P0/P1/P2 整改清单 + 复用边界** | 每条需求先对照：是否命中 P0 前置整改 / P1 一期演进 / P2 后续增强；命中 P0/P1 的按整改方案做，**不得沿旧路径叠加** |

### 2.2 复用判定流程（强制）

```text
接到需求
  → 查《优化建议清单》：是 P0/P1 整改项？
      ├─ 是 → 按整改方案实现（如敏感数据不可逆存储、金额用 BigDecimal、计价口径版本化），
      │        禁止在旧模型上打补丁（如在旧字段上叠加新业务语义）
      └─ 否 → 查 参考/：有现成技术件？
               ├─ 有 → 复用改造（改造成本 ≤ 重写 50%，超则 ADR 后重写）
               └─ 无 → 走原则一 framework4j；仍无 → 原则一 §1.2 两条出路
```

### 2.3 禁止行为（review 直接打回）

1. `参考/` 已有对应技术件却从零重写，且无 ADR；
2. 命中整改清单 P0/P1 项，却沿旧模型叠加扩展（典型：在旧字段上加条件表达新语义、在当前行数据上就地改口径、密钥/Key 继续存明文）；
3. 把遗留业务模型不加整改、原样包装成新平台能力。

### 2.4 参考工程目录豁免（需 ADR 留痕）

`adapter/`（原样复用的参考工程）源码零改动，视为第三方件等同物：

- **豁免**：其自带依赖/信封类/语言版本等框架强约束——这些红线仅约束本项目业务模块；
- **约束**：独立构建（不挂项目 parent POM）；升级整体替换（禁 cherry-pick 改源码）；
- 任何 adapter 与本项目服务的对接只走**配置**（yml/env），对接适配层写在业务侧。

## 原则三：四方对齐——对齐之前，任务不算结束

每个编码任务的 **Done 定义 = 文档、代码、测试、规范 四方对齐**：

| 方 | 对齐标准 | 检查方式 |
|---|---|---|
| 文档 | 行为先落 `docs/`（或修订现有章节）：表/接口/流程/向量与实现一致；修订历史追加 | 评审对照；文档↔代码 drift 由 CI 锚点检查 |
| 代码 | 实现与文档描述一致；命名/分层/包结构对齐架构与工程设计文档约定 | Code review + ArchUnit 架构测试 |
| 测试 | 测试向量先行（`// VECTOR:` 锚点）；覆盖门槛达标（领域层 90/80） | JaCoCo 门禁；向量锚点计数 |
| 规范 | mc-java-spec / mc-database-spec / mc-api-spec / mc-web-spec / mc-test 对应场景条款逐条过 | P0 必查项 grep（红线作业） |

**任务关闭清单**（全部打勾才可关任务）：

```text
□ 文档已更新（或确认无需更新）并追加修订历史
□ 代码与文档描述一致，ArchUnit/红线 grep 绿
□ 测试向量已写并绿，覆盖率达标
□ 规范 P0 必查项通过
□ 涉及 framework4j 缺口的，已走 1.2 两条出路之一并留痕
```

## 原则四：任务开始前，先扫 skills、尽量加载

任何任务动手前，先扫描 `.claude/skills/` 并按关键词加载相关技能（Skill 调用），带着规范写，不要写完再补：

| 任务类型 | 优先加载 |
|---|---|
| 任何后端编码 | `mc-java-spec`；涉及 framework4j 模块时对应 `fwk4j-*`（见 §1.1 映射） |
| 建表 / 写 SQL | `mc-database-spec` |
| 接口设计 / Controller | `mc-api-spec`（+ `fwk4j-api`/`fwk4j-web`） |
| 安全相关 | `mc-java-security`（后端）/ `mc-web-security`（前端） |
| 前端页面 / 组件 | `mc-web-spec` + `fc-web-sdk` |
| 测试编写 | `mc-test` |
| 缓存 / 监控 / 性能 | `mc-cache` / `mc-monitor` / `mc-perf` |
| 文档编写 | `mc-doc-arch/ad/dbd/api/prd` 对应文书 |

规则：**宁可多扫、不可漏载**；加载后以 skill 内规范为准绳（本文件与 docs/ 只做本项目特化约束）。

## 原则五：大任务分步交付，每步走"测试先行 + 评审循环"

### 5.1 分步规则

- 任务预估代码量**超过 1000 行**时，必须拆分为多个步骤，**每步 ≤ 1000 行代码**；
- 拆分按可独立对齐的最小闭环（一个聚合/一组接口/一个里程碑工作包），步骤粒度与 `docs/` 任务分解对齐；
- 每步都是一个完整交付单元：走完 5.2 流程且四方对齐（原则三）后，才进入下一步。

### 5.2 每步固定流程（TDD + 评审循环）

```text
① 写测试代码（向量先行，// VECTOR: 锚点）
② 写业务代码（实现到测试通过）
③ 跑测试（单测+集成，门禁按测试规范）
④ 修复（直到全绿）
⑤ 评审循环：对产出做评审 → 出 P0~P2 级优化建议 → 执行建议 → 修复 → 再评审
   退出条件：连续评审无 P0~P2 级建议，或已满 4 轮（仍遗留建议则记录到任务清单并升级人为决策）
```

- P0~P2 分级口径：P0 正确性/资损/安全，P1 一期演进必做，P2 不阻塞但应记录；
- 每轮评审建议与执行结果留在任务记录中（可追溯），**不得静默丢弃建议**；
- 4 轮上限是防停滞：到轮次仍有未消化的 P0/P1 建议时，停下来人为决策（改方案/降级/接受），不得无限循环。

## 红线速查（review 直接打回）

1. 重复实现了 framework4j 已有能力（§1.1 表中"禁止的自建行为"）；
2. framework4j 缺口未经人为确认就自建（§1.2）；
3. 动手前未查 `参考/` + 整改/优化建议清单（§2.2 复用判定流程）：`参考/` 有现成技术件却从零重写且无 ADR；或命中 P0/P1 整改项却沿旧模型叠加扩展（§2.3）；
4. 文档/代码/测试/规范任一方落后于其它三方就关闭任务（§3）；
5. 未扫 skills 直接开写（§4）；
6. 超 1000 行不分步，或步骤不走"测试→实现→测试→修复→评审循环"流程（§5）。
