# ADR-0005: 未读数=Redis 写时失效+回填+公告水位线；V1.0 轮询不推流

## 状态
proposed（2026-09-16，评审第 1 轮修订：增量计数改为写时失效）

## 上下文
铃铛角标高频读（30s 轮询/用户），未读数=定向消息未读+生效公告未确认。两个难点：①公告发布/下线是广播事件，中台无用户全集，无法按用户枚举失效缓存；②初稿「失效」与「增量计数」两节自相矛盾——增量方案 DB 提交后 N 个 INCR 非原子，Redis 故障丢增量即永久漂移且「miss 回填」修不了「key 存在但值错」。

## 备选方案
- A. 增量计数器：写路径 N 次 INCR（非原子、漂移不可修）
- B. 写时失效（cache-aside）：变更时 DEL，读 miss 查库回填
- C. WebSocket/SSE 实时推送：iframe 跨域连接管理复杂，90% 场景 30s 轮询可接受

## 决策
选 B + 公告水位线（评审第 3 轮升级口径）：定向未读数写时失效（**DB 事务提交后 DEL**，防回填竞态）；水位线 = `max(updated_at) over tenant_id IN (0,:tid)` 公告——**含平台公告**，发布/下线/定时任务置 EXPIRED 均变更 updated_at 自动覆盖，读取时重算比对（公告表千级行，SELECT max() 毫秒级）；`nfy:unread:*` 加 **TTL 1h** 兜底时间驱动变化（effective_at 定时到点）。未读数 key 仅用 Redis L2（关闭 Caffeine L1，防多实例 600s 陈旧窗口）。实时性：V1.0 轮询 30s + URGENT postMessage 通知父页；SSE 列为 V2.0 演进。

## 后果
正面：一致性可修复（删 key 即重推导）、失效逻辑简单；负面：公告发布瞬间该租户活跃用户缓存集中失效（未读部分索引查询 P99≤5ms，量级可承受）；角标非秒级实时（产品可接受）。
