# notification4j 业务线拆分与回归方案

> 2026-09-17 · 验收型全量回归：逐业务线测试 → 逐线报告+修复意见（不改代码）→ Playwright 截图取证 → 统一报告

## 一、拆分原则

按「最终用户/运营可感知的业务能力」切分，而非技术分层。每条业务线 = 一组闭环场景，
对应明确的契约清单、既有 IT 回归套件、新增 Playwright E2E 场景与证据形态。

## 三、回归方法

1. **双层验证**：每条线先跑既有 IT 套件（Testcontainers 深回归，保证语义层无回退），
   再跑新增 Playwright E2E（对真实运行的 fat jar 独立部署实例做端到端验证 + 取证）。
2. **证据**：
   - UI 流程 → 浏览器真实截图（`documents/test-report/screenshots/Lx-*.png`）；
   - 纯 API 流程 → Playwright request 发起，响应 JSON 渲染成证据页后截图（同目录，编号对应用例）。
3. **测试实例**（不改产品代码，仅运行时配置）：fat jar + JVM 参数提速引擎
   （scan 500ms / backoff `2,5,10`s / reaper 1s / 限速放宽），PG16+Redis7 独立容器（25432/26379）。
4. **缺陷处理**：发现问题只登记（P0~P3 + 修复意见），**不改产品代码**。

## 四、通过标准

- 既有 IT 套件：该线全部用例绿；
- Playwright E2E：该线全部场景绿且证据齐；
- 发现项均定级并给出修复意见；
- 八线完成 → 统一报告（总体结论/逐线矩阵/缺陷清单/证据索引）。
